Josbin POS — Architecture v3.1 · Built for Suriname

Three-layer enterprise POS platform: in-store Electron app, cloud Super Admin dashboard, open integration API. SRD-native, BTW-compliant, Dutch/English bilingual, AST timezone.

Three layers, one platform

Each layer is independently deployable and addresses a different audience. Layers 1 and 2 work together as one product (in-store + cloud). Layer 3 lets other POS vendors plug into the same data pipeline.

Layer 1

Store POS

Electron .exe on each terminal. Runs against a local Laravel/Postgres on one back-office PC. Sells without internet.

  • EPSON TM-T20 ESC/POS printing
  • USB HID + camera barcode
  • Hold bills, mixed payments
  • BTW correct discount-then-tax
  • Offline-first; cloud sync at Z-Report
Layer 2

Super Admin Dashboard

Browser-based, cloud-hosted. One Super Admin account per Josbin tenant; org-admin and store-manager scoped beneath.

  • Live multi-store revenue (Reverb WS)
  • Consolidated reports + BTW filings
  • Centralised catalogue → push to stores
  • Rekenkamer-ready signed audit export
  • User + license management
Layer 3

Open Integration API

REST endpoints + outbound webhooks. Third-party POS (or self-service kiosks, e-commerce) push sales in / pull reports out.

  • POST /v1/sales + /sales/batch
  • Idempotent via external_sale_ref
  • Outbound: sale.created, shift.closed, refund.issued
  • Auto-generated OpenAPI/Swagger
  • Sandbox for integration testing

Why this shape

  • Selling never depends on the internet. Paramaribo is reliable; Nickerie/Marowijne/interior are not. Each store has its own Postgres.
  • One client = one Super Admin. Each Josbin customer (the company you sell this to) gets their own dashboard, can onboard multiple organisations (their own customers).
  • Layer 3 is the moat. Government departments and franchises that already have a POS can keep it, route their data through Josbin, and still get the consolidated reporting / Belastingdienst exports.

Why Laravel 13

  • Eloquent = SQL injection structurally impossible
  • Reverb = native WebSocket server, no Pusher fees
  • Horizon = queue dashboard for free
  • AI SDK = OpenAI/Anthropic with same interface
  • Passkeys = phishing-proof Super Admin login

Why React 19.2 + Electron

  • Activity API = held bills pre-rendered, instant restore
  • React Compiler = auto-memoization, no useMemo noise
  • Electron = one .exe per terminal, DevTools off in prod
  • USB HID barcode scanners "just work" (keyboard wedge)
  • Same code runs in browser (manager screens) and desktop (POS)

Scoping invariants

  • Every query carries organisation_id, enforced at controller + custom validation rule (StoreBelongsToOrg) + policy.
  • Sales always have store_id; register_session_id is nullable (Layer 3 / API sales don't ring up on a till).
  • Stock is per-store (product_stocks table), not on the product. Row-locked during sale to avoid race conditions when two cashiers sell the last unit simultaneously.
  • Audit log is hash-chained and append-only — DB-level + Eloquent-level write protection. Even Super Admin can't delete a row.

What the cashier doesn't see

  • BTW pipeline — discount-then-tax order is enforced in BtwCalculationService (see BTW tab).
  • Idempotency — if the network blips and the UI retries, the second POST returns the same sale, not a duplicate.
  • Stock lock — concurrent sales of the last unit can't both succeed.
  • FX snapshot — the rate used is frozen on the sale row for audit; later rate changes don't rewrite history.
  • Async jobs — receipt email, anomaly detection, AI categorisation all happen on Redis queue after the sale row is committed.

Five-layer offline fallback

The local POS never blocks on the cloud. Sync happens opportunistically. If everything fails, there's a USB-export escape hatch so a shop in the interior can still get yesterday's data to head office.

Mobile data fallback

A 4G USB dongle (Digicel / Telesur) on the local server is the secondary path. It's only used for the sync payload (50–200 KB/day) — never for POS operations. Keeps mobile-data spend negligible for stores in the interior.

Audit trail

Days synced late are marked synced_late in the audit log, with both the original close timestamp and the sync timestamp. Rekenkamer auditors see the full picture, including the delay reason if noted.

BTW (Surinaamse VAT) — discount first, then tax

10% standard rate; basic foods + medicine flagged BTW-exempt. The order of operations is fixed by Belastingdienst Suriname compliance and verified by 50+ unit tests in BtwCalculationService.

Why discount-first matters

If you tax first and then discount, the BTW you remit to the Belastingdienst exceeds what the customer actually paid — over-collection. Discount-first calculates BTW on the actual money flow. Wrong order = audit finding.

Code & license protection

  • IonCube encodes all PHP before delivery — unreadable to humans, full speed inside Docker.
  • License key bound to hardware (MAC + CPU ID + UUID). Checks home every 24h with a 72h offline grace.
  • Renewal timeline: 30-day banner → 14-day banner → grace 14 days → soft lock (no new sales, all data + exports remain) → hard lock 30 days later → data export tools remain 90 days. Client data is never held hostage.
